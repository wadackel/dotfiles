# Shared agent scripts

Notes for `home/programs/agents/scripts/`, published at `~/.agents/scripts/`.

## abr (agent-browser auth state import)

`home/programs/agents/scripts/abr.ts` imports the running Chrome's cookies / localStorage / sessionStorage into `~/.agent-browser-state/main.json` for headless `agent-browser` replay. `home/programs/agents/default.nix` publishes the whole `scripts` directory at `~/.agents/scripts`, and `home/programs/zsh/init.zsh` wraps it in an `abr` zsh function.

- Tests: `bun test home/programs/agents/scripts/abr_test.ts` (a mock CDP server on `node:http` plus `ws`'s `WebSocketServer`, which under Bun is Bun's built-in implementation of that package; the tests spawn the script as a subprocess)
- It speaks CDP directly and **never attaches to a target it did not create**. Do not replace this with `agent-browser connect`: that attaches to every page target and calls `Page.enable`, and Chrome's frozen background-tab renderers never answer, so the daemon hangs (`Resource temporarily unavailable (os error 35)`)
- Cookies are narrowed to the tracked origins by RFC 6265 domain-match; `--all-cookies` disables it when SSO needs a third-party domain
- `~/.agents/` is shared: `skills` is owned by `home/programs/codex/default.nix`, `scripts` by `home/programs/agents/default.nix`

## rebase-guard (WIP-commit verification for the rebase skill)

`home/programs/agents/scripts/rebase-guard.ts` is called by the `rebase` skill after a rebase: the skill parks uncommitted changes in a `wip: auto-commit before rebase` commit instead of `git stash`, unwinds it with `git reset --mixed HEAD~1` once the rebase is done, and then runs `rebase-guard.ts verify <wip-sha>` to confirm that every file of the WIP commit is still in the working tree. It is published at `~/.agents/scripts/rebase-guard.ts` like `abr.ts`.

- Tests: `bun test home/programs/agents/scripts/rebase-guard_test.ts` (builds a bare origin plus clones under a temp dir and spawns the script as a subprocess)
- Per file it reverse-applies the WIP patch with `git apply --reverse --check` and reports `PRESENT`, `IN_HEAD` (already committed, e.g. the base absorbed it and the rebase skipped the WIP commit), `LOST` (file or mode gone), or `UNCONFIRMED` (patch no longer reverse-applies, typically because the base changed adjacent lines). Exit 0 only when nothing is LOST or UNCONFIRMED; exit 2 means the guard could not run (not a WIP commit, rebase in progress, internal git error) and is never a loss verdict
- It runs every git call from `git rev-parse --show-toplevel` and uses `--path-format=absolute --git-path` for the rebase-state check, so it works from subdirectories and inside linked worktrees; do not replace the reverse-apply with line-set comparison — a line that also exists elsewhere in the file would make a lost hunk look absorbed

## check-plan (plan-body lint for /plan)

`home/programs/agents/scripts/check-plan.ts` lints a plan file against the plan-body contract. Both plan skills (Claude `/plan`, Codex `$plan`) run it right after DRAFT and again before ACTIVATE; a plan with any `error` cannot be activated. Published at `~/.agents/scripts/check-plan.ts` like the other scripts in that directory (allow entry `Bash(*check-plan*)`, the same substring shape as `rebase-guard`).

- Rules: `section-missing` (error: `## Context`, `## Files to Change`, `## Task Outline`, `## Completion Criteria` and its `### Autonomous Verification` / `### Requires User Confirmation` / `### Baseline`), `av-tag-missing` (error: an Autonomous Verification bullet without `[file-state]` / `[orchestrator-only]` / `[live]` / `[outcome]`), `ruc-format` (error: a Requires User Confirmation item that is neither `- None` nor a `[live]` / `[orchestrator-only]` bullet in the five-field `Observe / Why not autonomous / Needs / Your steps / Needed by` form with values from the template vocabulary), `live-missing` (warn: no `[live]` under Autonomous Verification), `self-resolved-grade` (error: a `### Self-resolved` bullet without a `source:` outside backticks that is immediately followed by `[Direct]` / `[Supported]` / `[Inferred]`, only an `[Unknown]` there, a `[Direct]` with no backtick, `:N`, path-like token (a `/` with non-space on both sides), `$`-prefixed token, or `.<ext>` after it, or a `[Supported]` with nothing after it; the `[Direct]` message carries an example line; an absent section, zero bullets, a `(none)` paragraph, or a lone `- None` produce nothing), `section-duplicate` (error: the same heading line twice outside fences; the second occurrence is reported with the first one's line number, because a scripted `String.replace` whose replacement string expands `$` once duplicated part of a plan), `direct-excerpt` (warn: a `[Direct]` source with no `→ <output excerpt>` after the probe; the critic re-runs such a probe instead of reading the excerpt), `assumption-scope` (error: a `### Assumptions` bullet carrying `user-overridden: default` outside backticks with no `scope:` field; the rule that provisional defaults are for scope boundaries only was already in prose and was broken anyway). Headings match whole lines and fenced blocks are ignored, so the item-format section of a plan about plans does not trip it. `self-resolved-grade` checks syntax only — whether the cited probe actually yields the cited lines is the critic's reading of the quoted excerpt in its `### Round 1 evidence check` (or its re-run when there is none) and the adversarial pass (`home/programs/agents/shared/plan/references/contract.md` defines the grades)
- Tests: `bun test home/programs/agents/scripts/check-plan_test.ts` (fixtures are written to a temp dir at run time; no fixtures directory)
- The required headings and the `Needs:` / `Needed by:` vocabulary are constants in the script and must be changed together with the heading table in `home/programs/agents/shared/plan/references/contract.md` (mirrored in the Codex plan skill) and the item template line pinned by `codex-plan-clarification-contract_test.ts`; the `source:` template line is likewise pinned across both plan skills and `contract.md`
- It does not check line-number anchors or run any command from the plan: on real plans an anchor range check produced zero errors and dozens of warnings on deliberate path abbreviations, and the anchor mistakes that actually surface (bare `:N`, ranges pointing at the wrong prose) are not decidable from the file. Those stay with the DEEPEN critic and adversarial agent

## config-lint (repository configuration lint in `nix flake check`)

`home/programs/agents/scripts/config-lint.ts` is the second flake check next to `formatting` (`checks.config-lint` in `flake.nix` runs it with `bun --no-env-file --no-install --config=/dev/null` inside the Nix sandbox, where there is no `node_modules`; the script imports only `node:*` modules for that reason, and a test pins it). Published at `~/.agents/scripts/config-lint.ts`; run it by hand as `config-lint.ts .` from the repository root.

- Rules: `policy-parse` (error: a `- pattern:` line in the global `bash-policy.yaml` that is not `- pattern: "<glob>"`, or a policy with no rule), `skill-policy-conflict` (error: a command line inside a `bash` / `sh` / `shell` / `zsh` fence of a `SKILL.md` or `references/*.md` under `home/programs` that matches a bash-policy pattern; `<!-- config-lint: allow -->` on the line above the fence skips it, and vendored skill directories with a `.<vendor>-source` marker are skipped), `home-literal` (error: a `/Users/<name>` literal in `settings.json`, `hooks.json`, `*.nix`, `*.yaml`, `*.yml`, `*.json`; `$`, `*`, `{` after the slash are templates; `config-lint: allow` on the line or an entry in the script's `HOME_LITERAL_ALLOW` set exempts a line, the latter for strict JSON)
- Not covered: untagged fences, inline code spans, `exclude:` in the policy, heredoc bodies, and `cd x && git push origin renovate/y` compounds (the lint matches whole lines; the hook splits on the bash AST). The rule is preventive
- Tests: `bun test home/programs/agents/scripts/config-lint_test.ts` (temp-dir fixtures)

## vocab (the owner's vocabulary, injected at session start)

`home/programs/agents/scripts/vocab.ts` (entry), `vocab-lib.ts` (pure: read, lint, digest, apply) and `vocab-propose.ts` (material from sessions, the weekly packet) keep the owner's short-instruction vocabulary in the Obsidian vault, not in this repository: one note per term in `06_Vocabulary/`, the allowed kinds and relations declared in `06_Vocabulary/_schema.md`, and agent proposals in `98_Maintenance/proposals/Vocabulary/` until the owner sets `status: approved` in the `06_Vocabulary/語彙レビュー` Bases view. The `vocab` skill registers terms and drafts the weekly proposals; `/weekly-review` runs it.

- Injection: Claude and Codex run `vocab.ts hook claude|codex` on SessionStart (Codex's `hooks.json` is a store copy, so a change needs `darwin-rebuild`); opencode's `plugin.ts` adds the digest through `experimental.chat.system.transform`, once per session; Hermes `!claude` gets only the target repository's terms through `claude-task.ts` `repoVocabulary`. `VOCAB_DIGEST=off` turns injection off. Approved but unapplied proposals are part of the digest, pending ones never are
- Capture: the three memo scripts call `proposeFromSession` after their summary (Codex from `mainWorker`, never the 5-second Stop hook), through a lazy `import()` so a broken vocabulary module cannot stop the memo. It calls no model: it records corrections, answers to the agent's questions, and unregistered terms used twice in `~/.local/state/vocab/` (anything containing a `05_Private/` filename, `[[`, a URL or a token is dropped). Definitions are drafted weekly by the agent running `/weekly-review` from the packet `vocab.ts propose --weekly` prints — Haiku given a few excerpts proposed only generic tool names. At most five automatic proposals wait at a time
- Module layout: the memo scripts of `claude/`, `codex/` and `opencode/` and `vocab.ts` import `vocab-lib.ts`, `vocab-propose.ts` and `memo-shared.ts` by their real relative paths (`../../agents/…`); Bun resolves a script through its real path, so nothing is published next to them. After editing, run `bunx tsc --noEmit` from the repository root
- Approval: `vocab.ts add` only ever writes a pending proposal, even for a definition the owner dictated. It is in `permissions.allow`, so a direct write would let text injected into a session become approved vocabulary for every agent and for Hermes
- Tests: `bun test home/programs/agents/scripts/vocab-lib_test.ts home/programs/agents/scripts/vocab-propose_test.ts home/programs/agents/scripts/vocab_test.ts`

## plan-state / plan-evidence (shared evidence sidecar)

`home/programs/agents/scripts/plan-state.ts` (entry point, shebang) and `plan-evidence.ts` (library) are the evidence machinery shared by Claude `/impl` and Codex `$impl`; the commands (`init` / `start` / `require` / `snapshot` / `run` / `rerun` / `record` / `review` / `append-evidence` / `coverage` / `complete` / `reconcile`) and the check schema are described in `home/programs/codex/skills/impl/references/evidence.md`, and the fixed strings in `home/programs/agents/shared/plan/references/contract.md`. Published at `~/.agents/scripts/plan-state.ts`; running it with no arguments prints the usage with the check JSON shape and the status vocabulary.

- The target a record is bound to is the tree OID of the working tree (a copy of the index, `git add -A`, `write-tree`, with the index copy keeping the original's mtime so git's racy-clean rule still re-hashes a just-edited same-size file) plus the plan file. HEAD and the index are not part of it, so a commit or a stage of the same content keeps every record current; there is no gate generation. The objects go to `<plan>.objects/` next to the sidecar through `GIT_OBJECT_DIRECTORY` with `.git/objects` as an alternate, so a read-only `.git` (the Codex eval harness runs `-s workspace-write`) still works, and a stale rejection can `diff-tree` the recorded tree against the current one and name the paths that changed
- `run <evidence> task-N <id> [--expect-exit N] [--env K=V]... [--cwd DIR] [--grep RE] [--tail N] [--expect-unchanged] -- <argv>` snapshots, executes the argv without a shell (stdin ignored, its own process group), snapshots again and appends the record itself: `argv`, `cwd`, `exit`, `durationMs`, `tree`, `mutated` (paths the command changed; the target is the tree after the run) and the output cut to its first 4k and last 16k characters. It prints one status line (`pass|fail <id> exit=<n> <ms>ms mutated=<k>`) and the `--tail` lines or `--grep` matches, exits 1 on fail, and holds the sidecar lock only around the append (with a bounded retry, so two parallel `run`s both land). One check holds one argv; a `run` with a different argv supersedes the earlier one. `live`, `audit` and `review` checks still go through `snapshot` + `record`, and `record` rejects the fields only `run` writes
- `rerun <evidence>` re-executes every `run`-recorded check whose latest record is stale or `fail`, once per distinct argv, and lists the rest as `fresh` (passing at the current target) or `skipped (record)`; the argv set is fixed at the first read. The skills run it in the background on the final task and re-take the `skipped (record)` rows by hand before the gate
- `bash-policy.ts` inspects `plan-state.ts run` / `rerun` because `permissions.deny` and the bash-policy rules match a command as written and would never see the argv after `--`, and because the `run` / `rerun` command as a whole is what Claude Code judges (in auto mode the classifier, in manual mode a prompt): the call must be the whole Bash command (no prefix assignment, wrapper, `bash -c` string, pipeline or `&&`), the `--env` keys must be on the safe list in `RUN_ENV_KEYS`, no argv word may contain `$`, a backtick or `plan-state.ts`, the first argv word may not be a wrapper such as `timeout`, `nice` or `env` (`ARGV_WRAPPERS`; deny entries and the rules are anchored at the first word, so `timeout 9 git push -f origin main` would match only the allow entry for `timeout`), and the bare argv must pass the rules, then `permissions.deny` / `ask`, then `permissions.allow`, in that order; for `rerun` every stored argv in the sidecar is checked the same way, and an unreadable sidecar is refused. `splitRunArgs` in `plan-evidence.ts` is the one parser both sides use, loaded by the hook with a dynamic import so a broken `plan-evidence.ts` fails that check closed instead of disabling every rule. The hook judges the argv as the shell shows it, so the helper judges the argv it actually received as well: `assertArgvPermitted` in `plan-evidence.ts` re-reads the same settings and `bash-policy.yaml` (with its own glob matcher and a line-level YAML reader, because that file may import only `node:*`) right before `run` or `rerun` spawns, wherever `~/.claude/settings.json` exists (an environment variable would be one `env -u` away from switching it off; a machine without Claude Code has no allow list to mirror, and Codex runs every command without confirmation anyway). A brace expansion, `$` or a backtick in an inner word is refused by the hook because it cannot know the expanded form. The hook accepts `run` / `rerun` only as the whole command on a single line, and a passive subcommand (`snapshot`, `require`, `record`, …) at the head of any pipeline segment or `&&` chain with a quoted-delimiter heredoc (`<<'EOF'`) for stdin, but with no prefix assignment, `$(…)` or file redirect (a `GIT_CONFIG_PARAMETERS=…` prefix would reach the `git add` inside `snapshot`); every occurrence of the installed path `/.agents/scripts/plan-state.ts` must be one of those heads, because the allow entry that matches it would auto-approve the whole command (`command env -u X …`, `exec`, `find -exec sh -c`, `$(… snapshot …)`, a heredoc body), while the worktree path `home/programs/agents/scripts/plan-state.ts` as an argument of `sed` or `rg` is data and passes

- The sidecar `<plan basename>.evidence.json` must sit under `~/.codex/plans` or `~/.claude/plans`; whichever of the two exists is accepted (`plansDirs`), so a machine with one agent works. Every command also takes the plan's name (a word with no `/` that does not end in `.evidence.json`) in place of the path; `resolveEvidencePath` in `plan-evidence.ts` looks it up in those directories, refuses a name present in both, and is the one resolver both the helper and the bash-policy hook use, so the sidecar `rerun`'s stored argv are checked from is the one the helper replays. A name rather than "the only plan in progress" because abandoned sidecars stay in progress and `/autopilot` runs units in parallel
- The bookkeeping is implicit where it can be: the first `start` binds `repository`, and every later command runs git in that recorded root whatever the cwd (a drifted cwd used to fail as `repository mismatch`); `start task-N` completes each earlier in-progress task whose checks are current and leaves one that is not with a notice; `run` starts a pending task and declares an undeclared `cc-<n>` with the kind of the plan's n-th bullet, refusing `[live]`, `[outcome]` and an out-of-range n before writing anything; `review <path> <wave> -- <reviewers>` records the gate's verdict in one call. The explicit `start` / `require` / `complete` calls still work, because the Codex eval harness and plans already in flight use them
- `coverage <evidence>` reads the plan next to the sidecar and exits 1 listing every `### Autonomous Verification` bullet whose `cc-<n>` id (bullet order) no task requires; `[outcome]` bullets are numbered but never required. `complete` on the final task (`Final Audit + Review`) needs at least one `review` check; an `audit` check is accepted, not required
- Tests: `bun test home/programs/agents/scripts/plan-state_test.ts home/programs/agents/scripts/plan-evidence_test.ts` (git fixtures in temp directories, and a lock test that spawns the script)
- `plan-state.ts`, `plan-evidence.ts` and `check-plan.ts` import only `node:*` modules and each other, not `lib/proc.ts` or a package: the Codex eval harness (`home/programs/codex/evals/harness/runner.py`) copies just these three into a sandbox with no `node_modules`
- The default stdin of `plan-state.ts` is created lazily (`processStdin()`): under Bun, touching `process.stdin` on a command that never reads it keeps the process alive while the pipe stays open
- `permissions.allow` carries one `Bash(*/.agents/scripts/plan-state.ts <subcommand> *)` entry per passive subcommand and the two test paths, and no entry for `run` / `rerun`: auto mode drops a wildcarded interpreter such as `Bash(bun *)` and sends that command to the classifier, so an allow-listed `run` would let its inner `bun …` skip the review the direct command gets (the hook and the helper read the allow list as written and cannot tell which entries auto mode has dropped). A pre-existing `*name*` entry such as `Bash(*check-plan*)` can still approve a `run` whose option value, check id or path carries that name; anchoring those entries is a separate decision. The entries are per subcommand rather than the usual `Bash(*<script-name>*)`: a bare name would also match a same-named file in any reviewed repository, and `plan-state` is a plausible name to collide on
