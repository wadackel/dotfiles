# Accessibility review card
Trigger: `.css` `.scss` `.html`, or JSX markup in `.jsx` `.tsx`, among the changed files.
Scope: WCAG 2.2 and WAI-ARIA APG checks for `code-reviewer`. Layout bugs (z-index, flex) are not accessibility findings.

## Check
**Keyboard**
- A click handler on a `div` / `span` with no `<button>` or `<a href>`: unreachable by keyboard. A menu or "…" control is the usual case.
- Controls recreated on every render (buttons rebuilt in a render loop) lose keyboard focus; create once and update.
- `element.focus()` on re-render without `{ preventScroll: true }` pulls the list or page back to the element each time.
- Focus order follows visual order (no `tabindex > 0`); a modal or popover traps focus while open, Escape closes it, and focus returns to the opener.
- A visible `:focus-visible` style with enough contrast.
**Names and announcements**
- An icon-only button or an input with no visible label needs `aria-label` / `aria-labelledby` (a placeholder is not a label); `aria-labelledby` must point to an existing id.
- Status changes (saved, error, loading, count updated) announced through `aria-live="polite"` or `role="status"`; urgent errors `assertive`.
- Text cut off at narrow widths with the full text only in `title`: a `title` is not read by most screen readers or touch.
- Images: informative `alt`, decorative `alt=""`; SVG `role="img"` + `<title>` or `aria-hidden`.
**Semantics**
- Heading levels follow the outline; landmarks (`main`, `nav`) present and unique; `<ul>` / `<table>` + `<th scope>` for lists and tabular data.
- No redundant role on native semantics (`role="button"` on `<button>`); `aria-hidden` never on a focusable element.
- Information not carried by color alone; touch targets at least 24×24 CSS px.

## Do not flag
- Contrast ratios without computing them: list as a manual check, not a finding.
- Issues already in the baseline (pre-existing click-only divs): NIT only.
- React `aria-*` props with boolean values; React serializes them.
