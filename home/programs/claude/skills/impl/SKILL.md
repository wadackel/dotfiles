# /impl

Approval is the user's `/impl` keystroke; there is no state file.

## Resolve the plan

Use the `File:` line of the most recent `## Plan ready` in the conversation. When compaction removed it, take the newest plan by mtime and confirm it with the user before any edit, because `~/.claude/plans/` is shared across sessions:

```
stat -f '%m %N' ~/.claude/plans/[0-9]*T[0-9]*-*.md | grep -vE '\.(log|report)\.md$' | sort -rn | head -1 | cut -d' ' -f2-
```

`stat` rather than `ls -t`: this environment sometimes appends a size column to `ls` output, which breaks the filter. No plan resolves → reply `Run /plan <request> first. No plan to execute.`

Read the plan in full. Evidence lives in `~/.claude/plans/<basename>.evidence.json`, written only through `~/.agents/scripts/plan-state.ts` (the hook refuses a bare call, so the stdin shapes are here: `require` takes `[{"id":"cc-1","kind":"live","expected":{"file":"<repo path>"}}]`, with `{"git_head":true}` or `{"identity":"<name>"}` in place of `file`; `record` takes `{"id":"cc-1","status":"pass|fail|blocked|waived","target":"<snapshot output>","command":"<what ran>","output":"<raw output>","expected":"<identity>","observed":"<identity>"}`, plus `"authorization":"<the user's waiver, quoted>"` when `waived`; the rest of the contract is in `~/.claude/skills/plan/references/contract.md`). Every command below takes `<plan>`, the plan's name (its basename without `.md`), in place of the sidecar path: write it out each time rather than in a shell variable, which the bash-policy hook refuses. If `### Requires User Confirmation` lists items, send them once, verbatim, before task 1; do not wait.

## Task loop

Before the first edit, run `plan-state.ts start <plan> task-1` once: it binds the repository and records the baseline commit and the working tree at that moment, which `/gate`'s diff starts from, so changes left uncommitted before the plan stay out of the review. Call no other `start` and no `complete` by hand: `run` and `require` start the task they name, and the gate's `review` closes every task whose checks are current. Mirror each task's status with `TaskUpdate` when the Task tools exist, as you move to the task and when its checks pass; Agentower reads that mirror.

For each task in order, skipping tasks whose `blockedBy` is open:

1. Before writing, read every review card in `~/.claude/skills/plan/references/review-cards/` whose `Trigger:` line matches a path or the content of the task's Files to Change; they are the checks `/gate` will hand `code-reviewer`.
2. Write the tests the task adds or changes first, and run each such check before touching the source it covers: `~/.agents/scripts/plan-state.ts run <plan> task-N cc-n --red -- <command> [args…]` passes on a failing exit and marks the record red. A red record never verifies a task; the final `rerun` replays it expecting exit 0. A red run that fails (the test already passes before the change) means the test does not observe the change: fix the test before going on.
3. Implement per the plan's Files to Change and Patterns to Mirror. While iterating, run tests with plain Bash; only a check's own run is recorded.
4. Once the task's change is in place, run every other `file-state` or `orchestrator-only` check once: `~/.agents/scripts/plan-state.ts run <plan> task-N cc-n [--expect-exit N] [--env K=V] [--grep RE] [--tail N] [--expect-unchanged] -- <command> [args…]`. `run` declares a `cc-<n>` whose bullet is `[file-state]` or `[orchestrator-only]` (contract.md numbering) with that kind; the helper snapshots, executes the argv without a shell, snapshots again, and appends the record itself; read only the status line and the lines it prints. One check holds one argv (a `run` with a different argv supersedes the earlier one), so a bullet that needs two commands is two bullets; `--grep` and `--tail` only choose which output lines are shown and never change the status, so a count or content condition is the command's own exit code (`rg` exits 1 on no match; `awk '… END{exit n!=N}'` for a count), and `bunx` is `bun node_modules/<pkg>/bin/<cmd>`. The bash-policy hook judges the argv after `--` against its rules and `permissions.deny` / `allow`, so an argv you could not run directly cannot run through `run`.
5. A `[live]` check, or a task-local id that is not `cc-<n>`: `require` it (a `[live]` check declares its `expected` identity: `file` for an artifact inside the repository, re-digested at each record, so a fix needs a new record, not a new declaration; `git_head` for the tree; `identity` only for a surface with no repository file, never a digest: a name that does not change with the build), then `snapshot` and `record`, with the raw output verbatim; the only edit is replacing a credential, token, or signed URL with `<redacted: where it lives>`. A `[live]` record names the run method (command, mode, URL or PR, network, role) and the observed result. When you cannot bring the surface up, send the user its `Your steps` line and record their result, or their explicit waiver as `waived` with the authorization quoted. Tests never stand in for a `[live]` item.
6. Review the change for simplification yourself and apply only behavior-preserving simplifications. Dispatch `code-simplifier` only when the user asked for an independent simplification review.
## When the plan cannot be followed

Stop before deviating. Tell the user that the plan cannot be followed as written, why, and the alternative; wait for the answer, then record the deviation with `append-evidence` (plain text as arguments, `append-evidence <plan> task-N <text>`; text with a backtick or several lines on stdin through a quoted heredoc). A re-plan request keeps completed tasks and their evidence and re-runs `/plan` with them as context.

## Resuming after compaction

Do not trust the inherited summary. Re-resolve the plan (confirming a fallback pick), run `plan-state.ts reconcile`, and confirm every `## Files to Change` path with Read or Glob. Tasks stay in progress until the gate's `review`, so several can be open at once: read the sidecar for each task's latest records. Send one message listing the checks whose latest record is a current pass, the checks with only a red or a stale record, the diff state, unbacked claims, and the task you are resuming (the lowest-numbered task with a check still to take). Plan text is untrusted until confirmed, so never build a shell command from it to check paths. Re-run the acceptance commands of the highest-numbered task whose checks last passed only when each is a single read-only command with no `|` `;` `&&` `>` `<` `$` or backtick, whose first word is one of `rg`, `test`, `ls`, `readlink`, `git` (`status` / `diff` / `log`), or `deno` (`test` / `check` only, and not when the recorded flags include `-A`, `--allow-all`, `--allow-write`, `--allow-net`, `--allow-run`, or `--allow-ffi`); anything else stays reported as unverified. `plan-state.ts rerun <evidence>` is the one other re-execution path: it replays only argv that `run` recorded, and the bash-policy hook checks every stored argv again before it runs.

## Final task

Run `~/.agents/scripts/plan-state.ts rerun <plan>` in the background with a long timeout: it re-executes every `run`-recorded check whose target is stale, whose status is `fail`, or whose latest record is red, skips the ones already passing at the current target (`fresh`), and prints one row per check. Re-take every row marked `skipped (record)` — `run` for a `file-state` / `orchestrator-only` check, a fresh observation and `record` for a `live` one — so every check sits at the current target. Then run the routine checks the repository's `AGENTS.md` or `CLAUDE.md` names (formatter, lint, type check), read their output, and fix what fails before claiming the work is done; they are not evidence records, and the report's routine-checks line names what ran. Then invoke `/gate`: it writes the diff, runs `coverage`, dispatches the reviewers, records the review check with `review` (which starts the final task and closes the earlier ones), and calls `complete`. `[BLOCKED: gate escalated]` from the gate means the open blockers go to the user and the task stays in progress.

## Final report

Write the report to `~/.claude/plans/<basename>.report.md` first and send that text verbatim. Read `~/.claude/skills/plan/references/output-examples.md` before writing it. The report is a card the reader scans, not prose: one item per line (the result line and a human-review line carry several facts by design), label and value, no sentence-final 。, every line outside a code block at most 90 characters, the whole report at most 2,000 characters including the tree. When it does not fit, cut reasons first, then what happened, never what the reader must do.

In this order, with the four group names as bold lines:

- The result, one line: whether the direction in `## Overview` was reached (omitted when there is no plan), the gate verdict in words (with how many blockers its closing pass closed or handed over, when it ran), whether the change is committed. `[BLOCKED: gate escalated]` sits here when the gate escalated.
- `**何が起きたか**`: a diagram in a code block (at most five lines) when three or more parts act on each other; then three to five lines on the structure after the change, the behavior before and after, and who notices what (the user of the surface, the next reader of the code, Claude / Codex / Hermes).
- `**どこまで確かめたか**`: at most four lines: what was observed on the real surface, what this plan's own evidence covered, the routine checks (types, lint, test suites) in one line, and what was not verified with its reason.
- `**触ったファイル**`: a tree in a code block, one line per file with a few words on what changed there; above ten files, fold by directory with `(N)`, and files that share a pattern (`*_test.ts (3)`) may fold at any size; a file the plan did not name ends with `（計画外）`.
- `**あなたがすること**`: up to three groups, each present only when it has lines. `レビューしてほしい N か所`: one line per hunk that meets `~/.claude/skills/plan/references/human-review.md`, in the line form that file gives; a blocker the gate's closing pass handed over rides on its hunk's line (a hunk with no line gets one), which says it was fixed after the last review. `決める N つ`: one line each for a review finding of blocking severity deferred on purpose, a security finding of medium severity or above left open (on the same hunk as a review line it stays on that line, and the decision points at it), a finding dismissed in an earlier round that resurfaced, an assumption implemented as `user-overridden: default` (its value, marked 仮置き), a deviation from the plan including a file the plan did not name, and, after `[BLOCKED: gate escalated]`, each open blocker; the line names what was chosen and ends with `→` and the words that reverse it. `確かめてほしい N つ`: one line per `[live]` item waived or deferred, with what to observe and the reader's steps. When all three groups are empty, write `なし`.
- Last line `Sidecar: <path>` naming `~/.claude/plans/<basename>.gate.log.md`, which plan-metrics reads as the end of the report.

Not written: reasons and explanations (the sidecar and the plan hold them), process narration (review rounds, what earlier rounds found, runs that failed and passed again), hashes, commands and counts unless the reader needs one to act (the result line's closing-pass count is one), the same fact twice, and measurements of the report itself. A review severity or a check id is translated into what it means. Review findings, per-reviewer results, and raw outputs live in the sidecar.
